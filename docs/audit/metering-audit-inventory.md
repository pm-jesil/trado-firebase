## Design (decided before code)

| # | Decision | Alternatives rejected | Reason |
|---|---|---|---|
| DD-1 | One callable wrapper: `functions/src/services/callable.ts` exports `onCall` with the SDK's signature; the 35 callable files import it instead of `firebase-functions/v2/https`. It strips and validates `_meta`, opens the `RequestContext` (AsyncLocalStorage), times the call, records outcome and reason, and flushes the meter and audit. | A new `defineCallable()` API (rewrites 134 declarations); per-handler code (what exists now). | One import line per file; handlers, schemas and the export registry stay as they are. |
| DD-2 | `RequestContext` is filled in two steps: the wrapper sets request id, server time, `_meta`, truncated IP, user-agent family and App Check; the existing gate adds organization, membership, role and branch from the reads it already makes (no extra read). Triggers and the scheduled job open a system context (`source: trigger:<name>` / `scheduled:<name>`). | A second context resolver. | Prompt rule: extend, never a second engine; the gate already holds the trusted values. |
| DD-3 | One counting layer at the single `db` (`services/firebase.ts`): a Proxy over Firestore, references, queries, transactions, batches, bulk writer and aggregations counts every operation by the rules of 2.2 into the current context. No handler call site changes. | Migrating 53 files to a new data-access API; patching SDK prototypes in production. | Smallest change that sees every access; prototype patching stays free for the independent shadow counter in tests. |
| DD-4 | Limit counters (`usageCounterShards`) stay exact and keep their keys; they count calls. Cost metering is separate and counts operations. | Reusing the shards for cost. | Plan limits must stay exact and cheap; mixing them made today's labels wrong (P-2). |
| DD-5 | Cost rollups reuse `organizationUsageDaily` (key `{org}_{utcDate}`) for organization × day, with the client-reported numbers moved under `clientReported`; one new collection `userUsageDaily` (`{org}_{uid}_{utcDate}`) for organization × user × day. Both store quantities only (D-22) and carry `expireAt`. | A parallel `orgCostDaily`; per-request documents. | Reuse where the key fits; per-user needs its own key; per-request detail belongs in logs (Part 9). |
| DD-6 | Flush: `batched` (default) accumulates per (org, day) and (org, user, day) in instance memory and writes when the oldest entry is T s old or N calls accumulated, plus on SIGTERM; `exact` (tests) writes before the response. Meter writes use `FieldValue.increment` with merge (no read). | A write per request in production. | Overhead target ≤ 0.2 writes per request (5.5). |
| DD-7 | Audit is recorded by the layer: every commit (transaction, batch or single write) that changes a business document gets one event `auditLogs/{requestId}_{seq}` in the same commit; actions come from a registry keyed by callable; handlers may only add a reason (`noteAudit`). Denied, failed and read events are written by the wrapper, rate-limited. | Keeping handler-written audit (≈ 70 call sites, not atomic in places). | One recording point (D-23); atomic by construction. |
| DD-8 | `occurredAt` is a Firestore `Timestamp`; `auditLogsList` keeps returning `timestamp` (ISO) and the fields the Flutter app reads, computed from the stored event. | Renaming the response fields. | The Flutter app reads `timestamp`, `actorUid`, `entityType`, `entityId` (read-only grep); storage changes, the contract does not. |
| DD-9 | `storageUploadBytes` has one writer: the finalize trigger. Upload-session creation checks the limit without incrementing. | Keeping both. | Counts stored bytes once; abandoned uploads no longer counted (P-3). |
